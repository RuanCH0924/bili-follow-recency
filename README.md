## 项目简介

B 站的分发系统（关注列表、动态流、首页推荐）全都在回答同一个**正向问题**：*哪些 UP 主最近更新了？*

但没有人在回答**反向问题**：

> 我关注列表里，**哪些 UP 主已经很久没更新了？**

在一个积累了上百个关注的列表里，"最近还在活跃"和"早就停更退圈"的账号完全混在一起，用户根本不知道自己的关注列表有多"死"。

本插件就是补上这个盲区——它把关注列表按**停更时长**重新排序，让你一眼看出：

- 谁在偷懒（7 天～30 天没动静）
- 谁可能已经退圈（超过 30 天没动静）
- 谁最近还在正常产出

> 设计原则：**不抢 B 站的活**（"最近更新"B 站已经做好了），**只解决 B 站没解决的盲区**（停更无信号）。

## 快速开始

### 环境要求

- Chrome / Edge / 任意 Chromium 内核浏览器（内核版本 ≥ 88，支持 Manifest V3）
- **侧边栏模式需要 Chrome ≥ 114**；低于该版本时侧边栏按钮会自动隐藏，popup 模式不受影响
- 已登录的 B 站账号（插件依赖登录态 Cookie）

### 安装步骤

1. **下载源码**

   ```bash
   git clone https://github.com/RuanCH0924/bili-follow-recency.git
   ```

   或在 GitHub 页面点击 `Code` → `Download ZIP` 后解压。

2. **打开扩展管理页**

   在地址栏输入 `chrome://extensions/`（Edge 为 `edge://extensions/`）并回车。

3. **开启开发者模式**

   打开页面右上角的「开发者模式」开关。

4. **加载插件**

   点击左上角「加载已解压的扩展程序」，选择项目中的 **`prototype`** 目录（注意是 `prototype`，不是仓库根目录）。

5. **固定到工具栏**

   在扩展列表中找到「B站关注摸鱼博主」，点击拼图图标将其固定到工具栏。

### 首次使用

1. 确保浏览器中已登录 [bilibili.com](https://www.bilibili.com)
2. 点击工具栏中的插件图标打开 popup
3. 在 `UID` 输入框中填入你的 B 站 UID，点击「保存并查询」
4. 等待进度条跑完即可看到列表

> **UID 在哪找？** UID 就是你个人空间地址 `space.bilibili.com/` 后面那串数字，例如 `space.bilibili.com/23277571` 的 UID 就是 `23277571`。
>
> 首次打开插件时，列表区会直接给出这段说明并提供「打开 B 站获取 UID」按钮，点进去登录后地址栏里的数字就是你的 UID。
>
> 出于隐私考虑，代码中**不内置任何默认 UID**。`DEFAULT_UID` 常量位于 `popup.js` 顶部，如需固定一个常用 UID 可自行修改。

### 停更分组与颜色含义

列表按停更时长分为六组，顺序固定；每组内按最近更新时间倒序排列。分组头在滚动时会吸附在列表顶部。

| 分组 | 停更时长 | 状态色 | 含义 |
| --- | --- | --- | --- |
| 活跃 | < 7 天 | 绿 `#0d7a5f` | 正常更新 |
| 偷懒 | 7 天 ~ 1 个月 | 棕橙 `#b3541e` | 更新缓慢 |
| 久未更新 | 1 ~ 3 个月 | 灰 `#6b7587` | 明显掉队 |
| 长期断更 | 3 ~ 6 个月 | 深灰 `#5d6675` | 大概率停更 |
| 疑似退圈 | 6 个月 ~ 1 年 | 更深灰 `#4f5766` | 基本可以判断为停更 |
| 基本退圈 | > 1 年 | 最深灰 `#414856` | 建议清理 |
| 查询失败 | — | 红 `#c62828` | 数据获取失败，悬停可见原因 |

> 灰阶越深代表沉寂越久。红色仅用于「查询失败」，不表示停更等级。
>
> 深色模式下灰阶受对比度下限约束，相邻档差异比浅色模式小，分组语义主要由分组头文案传达。

### 标记说明

| 标记 | 含义 |
| --- | --- |
| `视频` / `专栏` / `动态` / `直播` | 最近一条内容的类型 |
| `置顶` | 最近一条动态是置顶内容，真实更新时间可能更早 |

### 批量取关

1. 勾选想要清理的 UP 主（左侧复选框）
2. 底部操作条点击「批量取关」
3. 在确认弹层中核对将被取关的名单，点击「确认取关」

## 反风控设置

B 站的风控系统会对短时间内的大量请求返回 `-352 风控校验失败`，表现就是列表里出现一批「查询失败」。插件提供了四项可调项，可在设置页逐项调整。

**默认值**：只有「设备指纹补全」默认开启（它没有速度代价）。「请求节奏拟人化」（会慢 30%~50%）与「风控熔断与自动恢复」（会让进度条停留 30~60 秒）**默认关闭**，需要你确认能接受代价后再开启。并发数默认 **3**。

**进入设置页**：点击 popup 顶部的齿轮按钮，或在扩展管理页点击「扩展程序选项」。

| 项目 | 默认 | 作用 | 代价 |
| --- | --- | --- | --- |
| 请求节奏拟人化 | 关 | 请求间隔加入 0~80ms 随机抖动、每处理 30 个插入 1~3 秒随机停顿、单条失败重试改为 0.9~1.4 秒指数退避 | 查询总耗时增加约 **30%~50%** |
| 并发数 | **3** | 同一时刻并行发出的请求数量，可选 1~5；全量查询与「重新查询失败的 UP 主」共用该值 | 越高越快，但同一时刻请求越密集、越接近批量抓取特征；并发 4~5 时一旦被风控，同批受影响的条目也更多 |
| 设备指纹补全 | **开** | 请求同时携带 `buvid3 / buvid4 / b_nut` 三个设备标识；缺少 `buvid4` 时自动向 B 站申请一次并长期缓存 | 首次会多一次网络请求；`buvid4` 会保存在浏览器本地存储中 |
| 风控熔断与自动恢复 | 关 | 识别 `-352 / -412 / -509 / -799` 后暂停整个队列，冷却 30~60 秒再自动继续；被拦截的条目会重试而不是判失败 | 触发时进度条会停留 30~60 秒（有倒计时文案）；单次查询最多冷却 3 次，超过则中止并提示稍后重试 |

> **这些设置只降低触发概率，不能保证完全不被风控。** 短时间内反复点刷新仍然容易被限制。
>
> 关注数不多（几十个）时，默认配置已经够用；如果经常撞上风控，再考虑开启「请求节奏拟人化」并适当降低并发数。
> 未开启「风控熔断」时，风控会退化为把当次条目直接标记为查询失败。

## 工作原理

### 整体流程

```
点击刷新
   │
   ├─ 1. 从 Cookie 读取 SESSDATA + buvid3（鉴权凭据）
   │
   ├─ 2. 分页拉取关注列表 /x/relation/followings（每页 50，自动翻页至 total）
   │
   ├─ 3. 对每个 UP 主并发（5 路）查询最近动态
   │        ├─ 主路径：/x/polymer/web-dynamic/v1/feed/space
   │        │           取回动态后按 pub_ts 自行排序，规避置顶污染
   │        └─ 兜底：  /x/space/upstat（标记 polluted，UI 打 ⚠ 提醒）
   │
   ├─ 4. 每完成一个 UP 主即时推送结果 → popup 边查边插入排序渲染
   │
   └─ 5. 全部完成后写入 chrome.storage.local 缓存
```

### 关键技术点

| 技术点 | 实现方式 |
| --- | --- |
| **防置顶污染** | 不信任接口返回的第一条动态，而是取回列表后按 `module_author.pub_ts` 自行降序排序 |
| **防 Service Worker 休眠** | popup 打开时通过 `chrome.runtime.connect({ name: 'keepalive' })` 建立长连接，查询期间 SW 不被回收 |
| **防并发双跑** | background 维护递增的 `runId` 令牌，每次启动新任务都会让旧任务失效，旧任务在批次边界自行退出 |
| **防数据串台** | 所有推送携带 `mid` 与 `runId`，popup 按当前 UID 过滤，切换 UID 时旧任务结果会被丢弃 |
| **防任务卡死** | 每次请求 10s 超时（`AbortController`），单 UP 主失败自动重试一次，查询中可随时取消 |
| **流式渲染** | 单个 UP 主结果就绪即用 `chrome.runtime.sendMessage` 推送，popup 按停更分组插入到组内正确位置 |
| **重排复用节点** | 分组 / 过滤 / 搜索变化时只移动需要移动的节点，不重建整个列表，300 条数据重排约 6ms |
| **配色继承** | 条目的等级色由所属分组通过 CSS 变量继承，节点跨组移动后颜色自动跟随 |
| **错误码语义化** | B 站返回的 `code` 映射为可操作的中文提示，原始 code 保留在括号内便于排查 |
| **主题切换** | 全套颜色走 CSS 变量，通过 `prefers-color-scheme` 切换明暗，深色色板单独验算对比度 |
| **限流规避** | 查询并发度 5、每批间隔 80ms；取关严格串行、间隔 400ms |
| **动态 ETA** | 基于已处理数量与实际耗时实时估算剩余时间，而非固定预估值 |

### 依赖的 B 站接口

| 接口 | 用途 | 鉴权 |
| --- | --- | --- |
| `/x/relation/followings` | 分页拉取关注列表 | `SESSDATA` + `buvid3` + `Referer` |
| `/x/polymer/web-dynamic/v1/feed/space` | 获取 UP 主最近动态（主路径） | 同上 |
| `/x/space/upstat` | 获取最新投稿时间（兜底，可能被置顶污染） | 同上 |
| `/x/relation/modify` | 取消关注（`POST`，`act=2`） | 同上 + `bili_jct`（csrf token） |

请求均携带以下 Header 以通过校验：

```http
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Referer: https://space.bilibili.com/
Origin: https://space.bilibili.com
Cookie: SESSDATA=xxx; buvid3=xxx
```

## 开发说明

本项目为**零依赖原生 JavaScript** 实现，不需要构建步骤，不需要 `npm install`。

### 修改代码

1. 直接编辑 `prototype/` 下的文件
2. 回到 `chrome://extensions/`，点击插件卡片上的 ↻ 重新加载
3. **注意**：修改 `background.js` 后必须重新加载扩展；仅修改 `popup.*` 时重新打开 popup 即可生效

### 调试

| 调试对象 | 打开方式 |
| --- | --- |
| popup | 右键插件图标 → 「审查弹出内容」 |
| Service Worker | `chrome://extensions/` → 插件卡片 → 「Service Worker」 |
| 存储内容 | DevTools → Application → Storage → Extension Storage |

### 打包发布

```bash
# 生成 dist/bili-follow-recency-v<版本>.zip（版本号自动取自 manifest.json）
node scripts/build-zip.js
```

脚本只打包 `prototype/` 目录，并自行写入 ZIP 结构以保证条目路径使用**正斜杠**。**请勿用系统自带压缩工具替代**——Windows 的 `Compress-Archive` 会写入反斜杠路径（`icons\icon-16.png`），不符合 ZIP 规范，会导致浏览器商店解析不到图标、跨平台解压产生错误文件名。

### 代码风格

- 原生 ES2020+ 语法，无框架、无构建工具
- DOM 操作统一在 `popup.js`，网络请求统一在 `background.js`，两者通过 `chrome.runtime.sendMessage` 通信
- 消息类型：`start` / `reset` / `cancel` / `query-state` / `refresh-one` / `unfollow`（popup → background），`item` / `progress` / `task-state` / `unfollow-progress`（background → popup）

## 常见问题

<details>
<summary><b>提示「未找到 SESSDATA，请先在 www.bilibili.com 登录」</b></summary>

插件需要读取你 B 站的登录 Cookie 来调用关注列表接口。

解决方法：
1. 打开 [bilibili.com](https://www.bilibili.com) 并确认已登录
2. 刷新一次 B 站页面
3. 回到插件重新点击刷新

若仍失败，请检查浏览器是否禁用了第三方 Cookie，或在 `chrome://extensions/` 中确认插件已获得 Cookie 权限。
</details>

<details>
<summary><b>我的 B 站 UID 在哪找？</b></summary>

UID 是你个人空间地址 `space.bilibili.com/` 后面那串数字。

两种获取方式：
1. 打开 [space.bilibili.com](https://space.bilibili.com)，地址栏会跳转到 `space.bilibili.com/数字`，那串数字就是你的 UID
2. 或直接点击插件空状态里的「打开 B 站获取 UID」按钮

拿到 UID 后填入插件顶部的 `UID` 输入框，点「保存并查询」即可。
</details>

<details>
<summary><b>查询到一半报错 / 部分 UP 主显示红色</b></summary>

通常是以下原因：
- **接口限流**：短时间内请求过于密集，等待几分钟后重试
- **登录态过期**：重新登录 B 站后重试
- **该 UP 主无公开动态**：账号已注销、被封禁或从无动态，属正常情况

点击「隐藏异常 / 显示异常」按钮可切换是否展示这些失败项，悬停红色文字可看到具体错误信息。
</details>

<details>
<summary><b>为什么查询这么慢？</b></summary>

B 站接口有限流，出于安全考虑插件将并发控制在 5、每批间隔 80ms。关注 100+ UP 主时通常需要几十秒。

查询期间会出现进度条和剩余时间估算。**查询在后台进行，你可以关闭 popup**，再次打开会显示当前进度。
</details>

<details>
<summary><b>为什么某个 UP 主显示的时间不准？</b></summary>

带 `可能不准` 标记的条目来自 `upstat` 兜底接口，该接口返回的"最新投稿时间"可能被 UP 主置顶的老视频覆盖。

正常情况下插件会走动态流接口并按发布时间自行排序来规避此问题，只有在动态流接口不可用时才会降级到兜底接口。
</details>

<details>
<summary><b>点刷新后列表一片空白，是卡住了吗？</b></summary>

不是。点击刷新会先清空旧列表，此时列表区显示「正在获取关注列表」，顶部进度条同步显示当前阶段与剩余时间估算。

- 如果长时间停在「获取关注列表」，多为登录态失效或接口限流，可点击右上角方块按钮停止后重新登录 B 站再试
- 如果全部 UP 主都查询失败，列表区会显示「N 个 UP 主查询失败」并提供「显示异常项」按钮，不会留下空白
</details>

<details>
<summary><b>批量取关安全吗？会不会误操作？</b></summary>

批量取关走的是 B 站官方取关接口，会**真实修改你的关注列表**。插件为此做了三层保护：

1. 必须手动勾选才会出现批量操作条，默认不选中任何项
2. 点击「批量取关」后会弹出确认层，逐条列出将被取关的 UP 主昵称
3. 取关严格串行执行（间隔 400ms），避免触发风控

失败的项目会保留勾选状态，方便你直接重试。**请务必在确认前核对名单。**
</details>

<details>
<summary><b>反复开关 popup 会重复查询吗？</b></summary>

不会。background 为每次运行分配递增的 `runId`，popup 打开时只查询当前任务状态并把自身加入消息监听，不会重复触发全量查询。

即使重复触发，旧任务也会因令牌失效而自动退出，不会产生并发请求。
</details>

<details>
<summary><b>切换 UID 后列表还是旧的？</b></summary>

这是预期行为。出于数据隔离考虑，切换 UID 会先中止后台旧任务，再清空当前列表与缓存并提示「UID 已保存」，需要手动点击刷新按钮才会拉取新数据。

这样做同时也避免了旧 UID 的查询结果混进新列表。
</details>

<details>
<summary><b>数据会上传到服务器吗？</b></summary>

不会。插件无任何后端服务，所有请求直连 `api.bilibili.com`，查询结果仅缓存在浏览器本地的 `chrome.storage.local` 中。
</details>

## 已知限制

- 仅展示关注列表中每个 UP 主的**最近一次**更新时间，不做历史趋势分析
- 动态流接口只取首页数据，若 UP 主在首页 10 条内无内容则降级到 `upstat` 兜底
- 分组顺序固定为「活跃 → 基本退圈」，不提供手动排序
- 搜索按昵称与 UID 做子串匹配，暂不支持拼音、正则或按停更时长筛选
- 导出仅支持 CSV，不包含图表
- 深色模式跟随系统设置，不提供插件内手动切换
- 侧边栏模式的宽度由浏览器侧边栏拖拽决定，过窄时部分文字会以省略号显示
- 反风控设置只能降低触发概率，无法完全避免 B 站风控；短时间内反复查询仍会被限制
- 仅适配 Chromium 内核浏览器，暂未适配 Firefox（Manifest V3 差异）

> 完整的体验问题清单、优先级与验收标准见 [docs/UX-AUDIT.md](docs/UX-AUDIT.md)。
