## 项目简介

B 站的分发系统（关注列表、动态流、首页推荐）全都在回答同一个**正向问题**：*哪些 UP 主最近更新了？*

但没有人在回答**反向问题**：

> 我关注列表里，**哪些 UP 主已经很久没更新了？**

在一个积累了上百个关注的列表里，"最近还在活跃"和"早就停更退圈"的账号完全混在一起，用户根本不知道自己的关注列表有多"死"。

本插件就是补上这个盲区——它把关注列表按**停更时长**重新排序，让你一眼看出：

- 谁在偷懒（7 天～30 天没动静）
- 谁可能已经退圈（超过 30 天没动静）
- 谁最近还在正常产出

> 设计原则：**不抢 B 站的活**（"最近更新"B 站已经做好了），**只解决 B 站没解决的盲区**（停更无信号）。

## 快速开始

### 环境要求

- Chrome / Edge / 任意 Chromium 内核浏览器（内核版本 ≥ 88，支持 Manifest V3）
- **侧边栏模式需要 Chrome ≥ 114**；低于该版本时侧边栏按钮会自动隐藏，popup 模式不受影响
- **「点击工具栏图标直接进入侧边栏」需要 Chrome ≥ 116**（依赖 `sidePanel.setPanelBehavior`）；114 ~ 115 上这条记忆不生效，图标仍然弹出 popup
- 已登录的 B 站账号（插件依赖登录态 Cookie）

### 安装步骤

1. **下载源码**

   ```bash
   git clone https://github.com/RuanCH0924/bili-follow-recency.git
   ```

   或在 GitHub 页面点击 `Code` → `Download ZIP` 后解压。

2. **打开扩展管理页**

   在地址栏输入 `chrome://extensions/`（Edge 为 `edge://extensions/`）并回车。

3. **开启开发者模式**

   打开页面右上角的「开发者模式」开关。

4. **加载插件**

   点击左上角「加载已解压的扩展程序」，选择项目中的 **`prototype`** 目录（注意是 `prototype`，不是仓库根目录）。

5. **固定到工具栏**

   在扩展列表中找到「B站关注摸鱼博主」，点击拼图图标将其固定到工具栏。

### 首次使用

1. 确保浏览器中已登录 [bilibili.com](https://www.bilibili.com)
2. 点击工具栏中的插件图标打开 popup
3. 在 `UID` 输入框中填入你的 B 站 UID，点击「保存并查询」
4. 等待进度条跑完即可看到列表

> **UID 在哪找？** UID 就是你个人空间地址 `space.bilibili.com/` 后面那串数字，例如 `space.bilibili.com/23277571` 的 UID 就是 `23277571`。
>
> 首次打开插件时，列表区会直接给出这段说明并提供「打开 B 站获取 UID」按钮，点进去登录后地址栏里的数字就是你的 UID。
>
> 出于隐私考虑，代码中**不内置任何默认 UID**。`DEFAULT_UID` 常量位于 `popup.js` 顶部，如需固定一个常用 UID 可自行修改。

### 停更分组与颜色含义

列表按停更时长分为六档，顺序固定；每组内按最近更新时间倒序排列。分组头在滚动时会吸附在列表顶部。
六档停更等级之外还有两个附加组：「无公开动态」与「查询失败」，它们都不是停更等级。

| 分组 | 停更时长 | 状态色 | 含义 |
| --- | --- | --- | --- |
| 活跃 | < 7 天 | 绿 `#0d7a5f` | 正常更新 |
| 偷懒 | 7 天 ~ 1 个月 | 棕橙 `#b3541e` | 更新缓慢 |
| 久未更新 | 1 ~ 3 个月 | 灰 `#6b7587` | 明显掉队 |
| 长期断更 | 3 ~ 6 个月 | 深灰 `#5d6675` | 大概率停更 |
| 疑似退圈 | 6 个月 ~ 1 年 | 更深灰 `#4f5766` | 基本可以判断为停更 |
| 基本退圈 | > 1 年 | 最深灰 `#414856` | 建议清理 |
| 无公开动态 | — | 中性灰 `#6b7587` | 请求成功但没有任何公开内容（账号注销 / 被封禁 / 从未发布），**不计入查询失败** |
| 查询失败 | — | 红 `#c62828` | 数据获取失败，悬停可见原因 |

> 灰阶越深代表沉寂越久。红色仅用于「查询失败」，「无公开动态」用中性色，两者都不表示停更等级。
>
> 深色模式下灰阶受对比度下限约束，相邻档差异比浅色模式小，分组语义主要由分组头文案传达。

### 标记说明

| 标记 | 含义 |
| --- | --- |
| `视频` / `专栏` / `动态` / `直播` | 最近一条内容的类型 |
| `置顶` | 最近一条动态是置顶内容，真实更新时间可能更早 |
| `可能不准` | 数据来自 `upstat` 兜底接口，可能被置顶视频覆盖 |
| `无公开动态` | 该 UP 主没有任何公开内容（账号注销 / 被封禁 / 从未发布），无法判断停更时长；不计入失败统计 |
| `查询失败` | 该 UP 主的数据获取失败，时间位置显示具体原因 |

### 批量取关

1. 勾选想要清理的 UP 主（左侧复选框）
2. 底部操作条点击「批量取关」
3. 在确认弹层中核对将被取关的名单，点击「确认取关」
4. 取关为串行执行（每次间隔 400ms），完成后成功项会从列表移除，失败项保留勾选以便重试

> ⚠️ 该操作会**真实修改你的 B 站关注列表**，且无法一键撤销。请务必核对名单后再确认。

## 反风控设置

B 站的风控系统会对短时间内的大量请求返回 `-352 风控校验失败`，表现就是列表里出现一批「查询失败」。插件提供了四项可调项，可在设置页逐项调整。

**默认值**：只有「设备指纹补全」默认开启（它没有速度代价）。「请求节奏拟人化」（会慢 30%~50%）与「风控熔断与自动恢复」（会让进度条停留 30~60 秒）**默认关闭**，需要你确认能接受代价后再开启。并发数默认 **3**。

**进入设置页**：点击 popup 顶部的齿轮按钮，或在扩展管理页点击「扩展程序选项」。

| 项目 | 默认 | 作用 | 代价 |
| --- | --- | --- | --- |
| 请求节奏拟人化 | 关 | 请求间隔加入 0~80ms 随机抖动、每处理 30 个插入 1~3 秒随机停顿、单条失败重试改为 0.9~1.4 秒指数退避 | 查询总耗时增加约 **30%~50%** |
| 并发数 | **3** | 同一时刻并行发出的请求数量，可选 1~5；全量查询与「重新查询失败的 UP 主」共用该值 | 越高越快，但同一时刻请求越密集、越接近批量抓取特征；并发 4~5 时一旦被风控，同批受影响的条目也更多 |
| 设备指纹补全 | **开** | 请求同时携带 `buvid3 / buvid4 / b_nut` 三个设备标识；缺少 `buvid4` 时自动向 B 站申请一次并长期缓存 | 首次会多一次网络请求；`buvid4` 会保存在浏览器本地存储中 |
| 风控熔断与自动恢复 | 关 | 识别 `-352 / -412 / -509 / -799` 后暂停整个队列，冷却 30~60 秒再自动继续；被拦截的条目会重试而不是判失败。**「自动重新查询失败项」阶段例外：一旦命中风控会直接停止重查并引导人工验证**，不再冷却续跑 | 触发时进度条会停留 30~60 秒（有倒计时文案）；单次全量查询最多冷却 3 次，超过则中止并引导你完成人工验证 |

> **这些设置只降低触发概率，不能保证完全不被风控。** 短时间内反复点刷新仍然容易被限制。
>
> 关注数不多（几十个）时，默认配置已经够用；如果经常撞上风控，再考虑开启「请求节奏拟人化」并适当降低并发数。
> 未开启「风控熔断」时，风控会退化为把当次条目直接标记为查询失败。

## 自动化设置

设置页的「自动化」区块提供两个开关，**默认都关闭**（两者都会增加请求量，需要确认能接受代价后再开启）。

| 项目 | 默认 | 作用 | 代价 |
| --- | --- | --- | --- |
| 自动更新 | 关 | 按设定频率在后台定期重新查询关注列表，频率可填 5 ~ 1440 分钟（默认 60 分钟） | 每次到点都会发一轮与手动刷新完全相同的请求，频率越高越容易被风控；浏览器未运行时不执行，到点时若已有查询在跑则跳过本轮 |
| 自动重新查询失败项 | 关 | 全部查询结束后自动补查失败的 UP 主，直到失败数归零；最多 10 轮，**命中风控**或连续 2 轮没有进展即停止并提示人工验证 | 会额外发几轮与手动重试相同的请求；失败无法解决时会多花几轮时间（最长约 4 分钟），期间可随时点停止中断 |

### 自动更新的计时锚点

计时从**上一次完整查询结束**的那一刻起算：

- 首次开启、修改频率后，从保存设置的那一刻起算一个完整周期
- 每次全量查询跑完（列表刷新结束、写入缓存时）都会重新起算；**随后补查失败项的时间不计入**，不会把下一次更新推后
- 手动点「批量重试」不会改变计时
- 到点时若已有查询正在进行，本轮跳过，等下一个周期
- 浏览器重启后若 `chrome.alarms` 定时器被清除（Chrome 不保证跨会话保留），会从启动时刻重新起算

### 自动重查的时间间隔与收敛条件

- 第 1 轮在全部查询结束后 **5 秒**开始，之后每轮递增 5 秒：10 / 15 / 20 / 25 秒……
- **单轮等待最长 30 秒**（第 6 轮起封顶），**最多重查 10 轮**
- 满足任一条件立即结束：**失败数归零** / **本轮命中风控** / **连续 2 轮失败数没有减少** / **达到 10 轮上限**
- 每轮只重查「仍然失败」的条目，救回一条就从待办里消失；等待期间进度条会显示「第几轮 / 10 + 倒计时」，随时可点右上角停止按钮中断

**命中风控**或**连续两轮没有减少**时会判定「再重试也没用」并停止（前者立即停、不再冷却续跑，继续撞只会让风控加深），同时在面板里提示：

> 请点击列表中任意一个「查询失败」的 UP 主进入其主页，在打开的 B 站页面里完成人工操作验证（这一步程序无法代替你），然后回来点「N 个失败」重新查询。

「无公开动态」的 UP 主不算失败，因此不会被反复重查。

### 实现说明

自动更新使用 `chrome.alarms` 定时唤醒 Service Worker，而不是 `setInterval`——Manifest V3 的后台脚本会被浏览器回收，定时器活不过休眠，只有 alarms 能可靠把它唤醒来跑任务。
定时器在浏览器启动、扩展更新与自动化设置变更时同步；已存在且间隔一致时不会重建，否则 Service Worker 每次被唤醒都会把计时重置，自动更新可能永远等不到触发。

## 工作原理

### 整体流程

```
点击刷新 / 自动更新到点 / 批量重试
   │
   ├─ 1. 从 Cookie 读取 SESSDATA + buvid3（鉴权凭据）
   │
   ├─ 2. 分页拉取关注列表 /x/relation/followings（每页 50，自动翻页至 total）
   │
   ├─ 3. 对每个 UP 主并发（默认 3 路，可在设置中调 1 ~ 5）查询最近动态
   │        ├─ 主路径：/x/polymer/web-dynamic/v1/feed/space
   │        │           取回动态后按 pub_ts 自行排序，规避置顶污染
   │        ├─ 兜底：  /x/space/upstat（标记 polluted，UI 打 ⚠ 提醒）
   │        └─ 两路都查不到内容 → 标记 noDynamic，归入「无公开动态」组（不算失败）
   │
   ├─ 4. 每完成一个 UP 主即时推送结果 → popup 边查边插入排序渲染
   │
   ├─ 5. 全部完成后写入 chrome.storage.local 缓存
   │
   └─ 6. 开启「自动重查失败项」时：等 5 秒 → 重查仍失败的条目 → 还有失败就等 10 秒 → 15 秒……
             （每轮等待 min(5×n, 30) 秒，最多 10 轮；失败归零或连续 2 轮无进展即停止）
```

### 关键技术点

| 技术点 | 实现方式 |
| --- | --- |
| **防置顶污染** | 不信任接口返回的第一条动态，而是取回列表后按 `module_author.pub_ts` 自行降序排序 |
| **防 Service Worker 休眠** | popup 打开时通过 `chrome.runtime.connect({ name: 'keepalive' })` 建立长连接，查询期间 SW 不被回收 |
| **防并发双跑** | background 维护递增的 `runId` 令牌，每次启动新任务都会让旧任务失效，旧任务在批次边界自行退出 |
| **防数据串台** | 所有推送携带 `mid` 与 `runId`，popup 按当前 UID 过滤，切换 UID 时旧任务结果会被丢弃 |
| **防任务卡死** | 每次请求 10s 超时（`AbortController`），单 UP 主失败自动重试一次，查询中可随时取消 |
| **流式渲染** | 单个 UP 主结果就绪即用 `chrome.runtime.sendMessage` 推送，popup 按停更分组插入到组内正确位置 |
| **重排复用节点** | 分组 / 过滤 / 搜索变化时只移动需要移动的节点，不重建整个列表，300 条数据重排约 6ms |
| **配色继承** | 条目的等级色由所属分组通过 CSS 变量继承，节点跨组移动后颜色自动跟随 |
| **错误码语义化** | B 站返回的 `code` 映射为可操作的中文提示，原始 code 保留在括号内便于排查 |
| **主题切换** | 全套颜色走 CSS 变量，通过 `prefers-color-scheme` 切换明暗，深色色板单独验算对比度 |
| **限流规避** | 查询并发度默认 3（可调 1 ~ 5）、每批间隔 80ms；取关严格串行、间隔 400ms |
| **动态 ETA** | 基于已处理数量与实际耗时实时估算剩余时间，而非固定预估值 |
| **定时唤醒** | 自动更新走 `chrome.alarms`（MV3 后台脚本会被回收，`setInterval` 活不过休眠）；已存在且间隔未变时不重建定时器，避免 Service Worker 每次唤醒都把计时重置。计时锚点固定为**上一次全量查询完成的时刻**（`restartAutoUpdateCountdown()` 在写缓存后、失败项自动重查之前重排），因此长耗时的补查不会把下一次更新推后 |
| **结果分类** | 「查到了但没内容」（`NoDynamicError` → `noDynamic` 标记）与「没查到」（`error`）在数据层分开，前者不进入失败统计与重查队列 |
| **失败重查循环** | 全量查询结束后按 5×n 秒（单轮上限 30 秒）递增等待补查失败项，每轮只重查仍失败的条目；失败归零 / 命中风控 / 连续 2 轮无进展 / 满 10 轮即结束，整个循环受 `runId` 约束，点停止或重新查询即中断 |
| **需人工介入的提示** | 自动重查命中风控或连续无进展时，任务以 `done` + `notice` 结束（而非 `error`），popup 用可关闭的提示条告知用户去某个失败 UP 主的主页完成 B 站人工验证。重查阶段通过 `stopOnRisk` 让风控直接停轮（全量查询阶段仍按设置冷却续跑），被拦条目照常记为失败、同批已成功的结果不丢 |
| **界面形态记忆** | 形态写进 `bili_ui.lastMode`（由 popup 页在自己的宿主里写入）；侧边栏形态下 background 会摘掉 `action` 的 popup 并打开 `sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` —— 否则有 popup 时点击图标只会弹窗，不会展开侧边栏 |

### 依赖的 B 站接口

| 接口 | 用途 | 鉴权 |
| --- | --- | --- |
| `/x/relation/followings` | 分页拉取关注列表 | `SESSDATA` + `buvid3` |
| `/x/polymer/web-dynamic/v1/feed/space` | 获取 UP 主最近动态（主路径） | 同上 |
| `/x/space/upstat` | 获取最新投稿时间（兜底，可能被置顶污染） | 同上 |
| `/x/frontend/finger/spi` | 浏览器缺少 `buvid4` 时申请一次并缓存（可关闭） | 同上 |
| `/x/relation/modify` | 取消关注（`POST`，`act=2`） | 同上 + `bili_jct`（csrf token） |

鉴权信息通过 Cookie 传递（`credentials: 'include'`），并显式附加设备标识：

```http
Accept: application/json, text/plain, */*
Accept-Language: zh-CN,zh;q=0.9
Cookie: SESSDATA=xxx; buvid3=xxx; buvid4=xxx; b_nut=xxx
```

> `User-Agent` / `Referer` / `Origin` 属于浏览器的**禁止修改头**（forbidden header），JS 设置会被静默忽略，因此代码中不再尝试伪造，实际发出的是扩展自身的来源特征。

## 开发说明

本项目为**零依赖原生 JavaScript** 实现，不需要构建步骤，不需要 `npm install`。

### 修改代码

1. 直接编辑 `prototype/` 下的文件
2. 回到 `chrome://extensions/`，点击插件卡片上的 ↻ 重新加载
3. **注意**：修改 `background.js` 后必须重新加载扩展；仅修改 `popup.*` 时重新打开 popup 即可生效

### 调试

| 调试对象 | 打开方式 |
| --- | --- |
| popup | 右键插件图标 → 「审查弹出内容」 |
| Service Worker | `chrome://extensions/` → 插件卡片 → 「Service Worker」 |
| 存储内容 | DevTools → Application → Storage → Extension Storage |

### 打包发布

```bash
# 生成 dist/bili-follow-recency-v<版本>.zip（版本号自动取自 manifest.json）
node scripts/build-zip.js
```

脚本只打包 `prototype/` 目录，并自行写入 ZIP 结构以保证条目路径使用**正斜杠**。**请勿用系统自带压缩工具替代**——Windows 的 `Compress-Archive` 会写入反斜杠路径（`icons\icon-16.png`），不符合 ZIP 规范，会导致浏览器商店解析不到图标、跨平台解压产生错误文件名。

## 常见问题

<details>
<summary><b>提示「未找到 SESSDATA，请先在 www.bilibili.com 登录」</b></summary>

插件需要读取你 B 站的登录 Cookie 来调用关注列表接口。

解决方法：
1. 打开 [bilibili.com](https://www.bilibili.com) 并确认已登录
2. 刷新一次 B 站页面
3. 回到插件重新点击刷新

若仍失败，请检查浏览器是否禁用了第三方 Cookie，或在 `chrome://extensions/` 中确认插件已获得 Cookie 权限。
</details>

<details>
<summary><b>我的 B 站 UID 在哪找？</b></summary>

UID 是你个人空间地址 `space.bilibili.com/` 后面那串数字。

两种获取方式：
1. 打开 [space.bilibili.com](https://space.bilibili.com)，地址栏会跳转到 `space.bilibili.com/数字`，那串数字就是你的 UID
2. 或直接点击插件空状态里的「打开 B 站获取 UID」按钮

拿到 UID 后填入插件顶部的 `UID` 输入框，点「保存并查询」即可。
</details>

<details>
<summary><b>查询到一半报错 / 部分 UP 主显示红色</b></summary>

红色的「查询失败」通常是以下原因：
- **接口限流**：短时间内请求过于密集，等待几分钟后重试（也可在设置页开启「自动重新查询失败项」让它自动补查）
- **登录态过期**：重新登录 B 站后重试
- **网络抖动 / 请求超时**：重试即可
- **B 站要求人工验证**：若自动重查命中风控或连续两轮都没有进展，会停止并提示你点击一个失败的 UP 主进其主页完成验证（这一步程序无法代替）

点击「隐藏异常 / 显示异常」按钮可切换是否展示这些失败项，悬停红色文字可看到具体错误信息。
</details>

<details>
<summary><b>「无公开动态」是什么意思？为什么不算查询失败？</b></summary>

这类 UP 主的两个接口都正常返回了，只是**确实没有任何公开内容**——常见于账号已注销、被封禁，或从未发布过视频 / 动态。

它是「查到了，但结果为空」，不是数据获取失败，所以单独归入「无公开动态」组、不计入失败统计，也不会被批量重试或「自动重新查询失败项」反复重查。

如果你认为其中某个账号其实有内容，可以点该行的刷新图标单独重查一次。
</details>

<details>
<summary><b>为什么查询这么慢？</b></summary>

B 站接口有限流，出于安全考虑插件默认并发 3（可在设置页调到 1 ~ 5）、每批间隔 80ms。关注 100+ UP 主时通常需要几十秒。

查询期间会出现进度条和剩余时间估算。**查询在后台进行，你可以关闭 popup**，再次打开会显示当前进度。
</details>

<details>
<summary><b>开了「自动更新」但好像没有生效？</b></summary>

先确认这几点：

1. 自动更新需要**浏览器处于运行状态**（可以是窗口最小化，但不能完全退出），它由 `chrome.alarms` 定时唤醒后台脚本执行
2. 到点时如果**已有查询正在进行**，本轮会跳过，等下一个周期
3. 频率按分钟填写，**最短 5 分钟**，默认 60 分钟；填小于 5 的数值会被自动修正为 5
4. 计时从**上一次完整查询结束**起算：首次开启或改动频率后要等一个完整周期才会看到第一次执行；之后每次全量查询完成都会重新起算（补查失败项的时间不计入）

每次自动更新都会发出与手动刷新相同的请求量；如果关注数很多、又常撞风控，建议把间隔放宽到 1 小时以上，或关闭该功能。
</details>

<details>
<summary><b>「自动重新查询失败项」会一直重查吗？</b></summary>

不会。它有四条停止条件，满足任意一条就结束：

- **失败数归零** → 正常收工
- **本轮命中风控（熔断）** → 立即停止（不再冷却续跑，继续撞只会让风控加深）
- **连续 2 轮失败数没有减少** → 判定再重试也没用，立即停止
- **达到 10 轮上限** → 停止，剩下的失败留给你手动重试

等待间隔为 5 秒起步、每轮递增 5 秒、单轮最长 30 秒，所以即使跑满 10 轮也只多花约 4 分钟。

若因「命中风控」或「连续 2 轮没有减少」而停止，面板会提示这通常是 B 站要求人工操作验证：请点击列表中任意一个「查询失败」的 UP 主进入其主页，在打开的 B 站页面里完成验证（这一步程序无法代替你完成），然后回来点「N 个失败」重新查询。
</details>

<details>
<summary><b>为什么某个 UP 主显示的时间不准？</b></summary>

带 `可能不准` 标记的条目来自 `upstat` 兜底接口，该接口返回的"最新投稿时间"可能被 UP 主置顶的老视频覆盖。

正常情况下插件会走动态流接口并按发布时间自行排序来规避此问题，只有在动态流接口不可用时才会降级到兜底接口。
</details>

<details>
<summary><b>点刷新后列表一片空白，是卡住了吗？</b></summary>

不是。点击刷新会先清空旧列表，此时列表区显示「正在获取关注列表」，顶部进度条同步显示当前阶段与剩余时间估算。

- 如果长时间停在「获取关注列表」，多为登录态失效或接口限流，可点击右上角方块按钮停止后重新登录 B 站再试
- 如果全部 UP 主都查询失败，列表区会显示「N 个 UP 主查询失败」并提供「显示异常项」按钮，不会留下空白
</details>

<details>
<summary><b>批量取关安全吗？会不会误操作？</b></summary>

批量取关走的是 B 站官方取关接口，会**真实修改你的关注列表**。插件为此做了三层保护：

1. 必须手动勾选才会出现批量操作条，默认不选中任何项
2. 点击「批量取关」后会弹出确认层，逐条列出将被取关的 UP 主昵称
3. 取关严格串行执行（间隔 400ms），避免触发风控

失败的项目会保留勾选状态，方便你直接重试。**请务必在确认前核对名单。**
</details>

<details>
<summary><b>反复开关 popup 会重复查询吗？</b></summary>

不会。background 为每次运行分配递增的 `runId`，popup 打开时只查询当前任务状态并把自身加入消息监听，不会重复触发全量查询。

即使重复触发，旧任务也会因令牌失效而自动退出，不会产生并发请求。
</details>

<details>
<summary><b>切换 UID 后列表还是旧的？</b></summary>

切换 UID 时插件会先中止后台的旧任务、清空旧缓存与搜索条件，然后立即发起新 UID 的查询，列表会重新从空列表开始填充。

如果列表迟迟没有变化，多半是新 UID 的查询失败了，检查顶部提示条与统计区即可看到原因。
</details>

<details>
<summary><b>点工具栏图标不弹窗了，直接打开了侧边栏，怎么改回去？</b></summary>

插件会记住你上次使用的形态：**上次是从侧边栏打开的，下次点击工具栏图标就直接展开侧边栏**（不再弹 popup），这样就不用每次先弹窗再点一次「打开侧边栏」。

想改回弹窗模式：打开侧边栏，点击页头里的「切换回弹窗」按钮（那颗窗口图标），看到「已切换为弹窗模式」的提示后，下次点击工具栏图标就恢复为弹窗。

该行为依赖 `chrome.sidePanel.setPanelBehavior`，需要 Chrome / Edge ≥ 116；更低版本上这条记忆不生效，图标始终弹出 popup。
</details>

<details>
<summary><b>数据会上传到服务器吗？</b></summary>

不会。插件无任何后端服务，所有请求直连 `api.bilibili.com`，查询结果仅缓存在浏览器本地的 `chrome.storage.local` 中。
</details>

## 已知限制

- 仅展示关注列表中每个 UP 主的**最近一次**更新时间，不做历史趋势分析
- 动态流接口只取首页数据，若 UP 主在首页 10 条内无内容则降级到 `upstat` 兜底
- 分组顺序固定为「活跃 → 基本退圈（→ 无公开动态 → 查询失败）」，不提供手动排序
- 搜索按昵称与 UID 做子串匹配，暂不支持拼音、正则或按停更时长筛选
- 导出仅支持 CSV，不包含图表
- 深色模式跟随系统设置，不提供插件内手动切换
- 侧边栏模式的宽度由浏览器侧边栏拖拽决定，过窄时部分文字会以省略号显示
- 反风控设置只能降低触发概率，无法完全避免 B 站风控；短时间内反复查询仍会被限制
- 「自动更新」要求浏览器处于运行状态，且两次生效之间至少间隔 5 分钟；浏览器完全退出期间不会补跑
- 「自动重新查询失败项」最多 10 轮、单轮等待最长 30 秒；命中风控或连续 2 轮失败数没有减少时会停止并提示人工验证，此时重试已无效，需按提示进一次 UP 主主页完成验证
- 仅适配 Chromium 内核浏览器，暂未适配 Firefox（Manifest V3 差异）

> 完整的体验问题清单、优先级与验收标准见 [docs/UX-AUDIT.md](docs/UX-AUDIT.md)。
