## 总体结论

| 维度 | 现状评分 | 核心判断 |
| --- | --- | --- |
| 功能易用性 | 6/10 | **"能查"但"不能用完"**：发现停更 UP 后无法收口解决问题；首次使用引导缺失；查询过程不可控 |
| 交互体验 | 5/10 | **存在 2 处数据正确性缺陷**（切换 UID 串台、并发双跑），反馈机制薄弱，键盘不可达 |

共识别 **47 项**待调整项：P0 阻断级 5 项、P1 体验级 19 项、P2 打磨级 23 项。

**优先级定义**

| 级别 | 定义 |
| --- | --- |
| `P0` | 阻断级：导致数据错误、结果不可信、流程卡死或用户无法理解当前状态 |

## 一、功能易用性审查

### 1.1 现有功能流程梳理

```
打开 popup
 ├─ 有缓存 → 直接渲染列表
 └─ 无缓存 → 空状态"点击刷新开始查询"
      ↓
   填 UID → 点「保存」→ 列表清空 → 提示"UID 已保存，点刷新按钮开始查询"  ← 断点 1：两步操作
      ↓
   点「刷新」→ 进度条跑完 → 列表按停更时长排序
      ↓
   发现摸鱼 UP 主 → 点一行 → 跳转 B 站主页 → 手动取关                    ← 断点 2：任务未闭环
```

**关键结论：插件的核心价值主张是"帮你清理关注列表"，但当前只完成了"诊断"（发现问题），缺失"治疗"（批量取关）。** 用户发现 30 个停更账号后，仍需手动跳转 30 次主页逐一取关，核心任务路径被截断。

### 1.2 待调整项

| 编号 | 问题 | 修改方向 | 验收标准 |
| --- | --- | --- | --- |
| **F1**<br>`P0` | 核心任务未闭环：仅能跳转主页，无法批量取关，用户需重复 30+ 次手动操作 | 列表项增加勾选态，底部固定操作条提供「批量取关」「批量打开主页」「复制 UID 列表」 | 勾选 ≥2 个停更 UP 后可一键取关；操作前有二次确认；失败项可单独重试 |
| **F6**<br>`P0` | 全部 UP 主查询失败时，异常项默认隐藏 → 列表空白，但顶部显示"已查 132 / 132"，用户完全无法理解发生了什么 | `rerenderList` 增加"筛选后为空"分支，渲染专用空状态并直接给出「显示 N 个异常项」按钮 | 构造全失败场景时，列表区显示"N 个 UP 主查询失败 + 一键显示异常"，不再出现空白 |
| **F9**<br>`P0` | 无请求超时、无取消入口：`biliFetch` 未使用 `AbortController`，接口挂起则永久转圈无法恢复 | 单请求 10s 超时；单 UP 失败重试 1 次；查询中提供「停止查询」按钮 | 断开网络后 10s 内进入错误态；查询中可随时中断，按钮恢复可用 |
| **F2**<br>`P1` | 首次引导缺失：仅提示"输入你的 B 站 UID"，但用户不知道 UID 在哪找、是什么 | 空状态补充图文说明：`space.bilibili.com/` 后数字即 UID，并提供「打开我的空间」快捷入口 | 新用户不看文档即可完成首次查询；引导文案含 UID 获取路径 |
| **F3**<br>`P1` | 「保存 UID」与「开始查询」被拆成两步，且保存后需用户自行寻找右上角刷新按钮，反直觉 | 合并为「保存并查询」；仅在 UID 变更时触发；无变化时按钮置为禁用态 | 修改 UID 后一次点击即出结果，操作步骤从 2 步降为 1 步 |
| **F4**<br>`P1` | 排序方向、异常过滤偏好不持久化，每次打开 popup 都重置为"最新优先/隐藏异常" | 将 `sortDir`、`hideErrorItems` 写入 `chrome.storage.local`，启动时读取 | 设为"最旧优先"后关闭再打开，仍保持"最旧优先" |
| **F5**<br>`P1` | 数据时效不可见：缓存 `ts` 字段已写入但从未展示，用户不知道看到的是 1 分钟前还是昨天的数据 | header 状态区展示「更新于 X 分钟前」，超 24h 转为警示色 | 打开 popup 可见数据时间；缓存超 24h 时时间戳变色提示 |
| **F7**<br>`P1` | 统计文案"已查 89 / 132"口径混乱：分子含被隐藏的异常项，分母在缓存态下退化为本地条数 | 明确区分口径，改为「已查询 89 / 共 132 个关注」，并在有异常时追加「（3 个失败）」 | 任何状态下分子分母含义唯一且可自解释，不出现"89/89 但列表为空" |
| **F8**<br>`P1` | 无搜索功能：关注 300+ 时无法定位特定 UP 主，只能滚动翻找 | header 增加搜索框，按昵称/UID 实时过滤 | 输入关键词后列表在 200ms 内过滤完成，命中为空时有提示 |
| **F10**<br>`P2` | 无法只刷新单个 UP 主，只能整体重查 | 列表项 hover 显示单项刷新图标 | 单项刷新不影响其他条目 |
| **F11**<br>`P2` | 错误码直出：`code=-101`、`code=-412` 原文展示，用户无法据此行动 | 建立错误码映射表（-101 → "登录已过期，请重新登录 B 站"；-412 → "请求过于频繁，请稍后再试"） | 常见错误码展示为可操作的中文提示，原始 code 收进 title |
| **F12**<br>`P2` | 无法导出活跃度数据 | 支持导出 CSV / Markdown 报告 | 导出文件含昵称、UID、最后更新时间、停更天数、类型 |
| **F13**<br>`P2` | 分级只有 7/30 天三档，与路线图承诺的"90 天退圈档"不统一，缺少强信号 | 增加 > 90 天"疑似退圈"档，并支持按等级分组展示 | 停更 > 90 天的 UP 主有区别于"偷懒"的强视觉标识 |
| **F14**<br>`P2` | 无手动清空缓存入口，用户只能靠切换 UID 间接触发 | 增加「清空缓存并重查」入口 | 可一键清除本地缓存 |

## 二、交互体验审查

### 2.1 数据正确性缺陷

| 编号 | 问题 | 修改方向 | 验收标准 |
| --- | --- | --- | --- |
| **I1**<br>`P0` | **切换 UID 竞态串台**：查询进行中修改 UID，`background` 的旧任务仍在推送 `item` 消息，`popup.js` 监听器无差别插入 → 新 UID 的列表里混入旧 UID 的 UP 主，进度条也继续显示旧任务进度 | `item` / `progress` / `task-state` 消息体统一携带 `mid`，popup 按当前 `currentUid` 过滤；同时在切 UID 时向 background 发送取消指令 | 在查询进行中切换 UID，新列表不出现任何旧 UID 的 UP 主，进度条归零重置 |
| **I2**<br>`P0` | **并发双跑**：`background.js` 的 `reset` 分支直接把 `task.status` 强制置为 `idle`，而旧 `runTask` 循环仍在执行 → 两个任务并发请求，重复项插入、API 请求量翻倍，可能触发风控 | 引入递增 `runId` 令牌，`runTask` 每轮校验令牌，过期即中止；或真正实现 `AbortController` 取消旧任务 | 查询中连续点击刷新，最终列表无重复项，Service Worker 网络面板无并发重复请求 |

### 2.2 反馈机制与逻辑连贯性

| 编号 | 问题 | 修改方向 | 验收标准 |
| --- | --- | --- | --- |
| **I3**<br>`P1` | 刷新按钮存在**无法恢复的禁用态**：点击后 `$btn.disabled = true`，仅 `done` / `error` 会恢复；而 `start` 消息在任务运行中返回 `skipped`，该分支不做任何 UI 恢复 → 按钮永久置灰 | 统一 `done` / `error` / `skipped` 三态均恢复按钮；补充 3s 兜底超时解锁 | 任何路径下按钮均可恢复可点击态，无永久置灰场景 |
| **I4**<br>`P1` | **排序/过滤触发全量重排**：`rerenderList()` 清空 `$list` 后重建全部 DOM 节点，重播 `fadeIn 0.3s` 动画 → 200+ 项时明显闪烁与卡顿 | 不重建节点，仅复用现有 `li` 调整 DOM 顺序（`insertBefore` / `appendChild`）；排序切换只加一次位移动画 | 300 项列表切换排序在 100ms 内完成，无整屏闪烁 |
| **I5**<br>`P1` | 无查询完成反馈：进度条直接消失，用户不确定是"查完了"还是"崩了" | 完成时进度条过渡到 100% 后淡出，同时状态区显示「更新于 刚刚」 | 查询结束有明确的完成态视觉回调 |
| **I6**<br>`P1` | 错误提示位置错误：`#error` 位于列表容器之后，长列表时被推到页面底部，用户根本看不到失败原因 | 错误条上移至 header 下方并 `position: sticky` | 任何滚动位置下错误提示均可见 |
| **I7**<br>`P1` | 错误提示无法关闭，只能等下次刷新被动清除，且排序/过滤等无关操作不会清除它 | 增加关闭按钮；用户执行任何主动操作后自动清除陈旧错误 | 错误可手动关闭，且不会在无关操作后残留 |
| **I8**<br>`P1` | **键盘与无障碍完全缺失**：列表项是 `li + click`，无法 Tab 聚焦、无 Enter 激活；进度条是普通 `div` 无 `role="progressbar"`；排序/过滤按钮无 `aria-pressed`；无 `:focus-visible` 样式 | 列表项改用 `<a>` 或加 `tabindex + role="button" + keydown`；补齐 ARIA 角色与状态；增加焦点样式 | 全流程仅用键盘可完成（Tab 遍历 + Enter 激活），Lighthouse 无障碍得分 ≥ 90 |

### 2.3 交互规范建议

**① 状态模型**：popup 必须显式建模六态，互斥且唯一。

| 状态 | 触发 | 必备 UI |
| --- | --- | --- |
| `idle` | 无缓存且未查询 | 空状态 + 主操作按钮 |
| `loading` | 查询中 | 进度条 + 已用时长 + 取消按钮 |
| `success` | 查询完成且有可见项 | 列表 + 数据时间戳 |
| `empty` | 查询完成但可见项为 0 | 分两种文案：真无关注 / 全被过滤 |
| `partial` | 部分失败 | 列表 + 顶部「N 个失败」可展开条 |
| `error` | 整体失败 | 顶部错误条 + 重试按钮 |

**② 反馈时限基线**

| 耗时 | 反馈要求 |
| --- | --- |
| < 100ms | 按下态 |
| > 400ms | 显示 loading 指示（按钮转圈 / 骨架屏） |
| > 3s | 显示进度条 + 剩余时间 |
| > 10s | 必须提供取消入口 |

**③ 文案规范**：动词开头 / 给出下一步 / 不直出技术码 / 不使用指代外部位置的句子（应把按钮放进空状态内）。

**④ 动效规范**：统一 `200ms cubic-bezier(0.4, 0, 0.2, 1)`；新增 `prefers-reduced-motion: reduce` 分支关闭所有装饰性动画；单次动画元素数 > 50 时禁用进场动画。

## 三、视觉设计审查
